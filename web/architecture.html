Decisions and their tradeoffs

The server is the referee

Clients send inputs, never results. The server owns the clock, checks every answer and hands out every point. Fix options only reach a player after they find the broken line, and the real fix is mixed in with other bugs the factory proved fail the tests.

Tradeoff: every action costs a round trip. At 10 updates a second that is invisible for this game.

Player code never runs on the server

A fix is accepted when it matches the right line token for token, ignoring spacing and quote style. Nothing a player types is ever executed.

Tradeoff: a different-but-correct fix is rejected, so every bug is kept to a single small change and the game says so.

Puzzles come from mutation testing

The bug factory swaps one token at a time (< for <=, && for ||, +1 on a number), compiles the result and runs the real tests. Bugs that change nothing are thrown away; endless loops become "never finishes" clues.

Tradeoff: it runs at build time, not on startup, so the free server boots instantly. A test fails if the saved puzzles drift from the code.

A WebSocket server with no library

The protocol is small enough to own: handshake, masking, length encoding, ping and close. Unmasked, oversized, fragmented or cross-site traffic is refused.

Tradeoff: no compression or fragmented messages. Game messages are tiny, so neither is needed.

Anti-cheat by server timing

Keystrokes are timed when they arrive, so a client cannot lie about its speed. More than 25 characters at once counts as a paste, and faster than about 200 words a minute is flagged.

Tradeoff: a determined bot typing at human speed, or a modified client that works out which option the others are all built from, still gets through. That is the honest limit of any browser game.

One instance, in memory

The free host runs a single process, so rooms, logs and leaderboards live in memory and reset on a restart.

To scale: route each room code to one instance (sticky by code), keep leaderboards in a shared store, and rebuild any room from its event log.

Replays come from the event log

Nothing is filmed. A replay is the match's event log plus its rounds, played back in the browser. The same events that decided every score rebuild every frame.

Tradeoff: the server keeps only the last 30 replays, in memory, and bots' typing is interpolated between their recorded finishes.

Your code runs in your browser

Custom games are tested in a Web Worker in the creator's own browser. The server only receives puzzle IDs and clues, re-plants the bugs from the source text, and rejects anything it can't rebuild.

Tradeoff: the server has to trust the clue text, but only the creator's own room ever sees it.
